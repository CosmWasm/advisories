# CWA-2026-006: Sandbox escape in the Wasmer Singlepass compiler

**Severity**

Critical

Fund loss

**Affected versions:**

- wasmd ≤ `v0.70.3`, ≤ `v0.61.14`, ≤ `v0.60.8`, ≤ `v0.54.9`
- wasmvm ≤ `v3.0.7`, ≤ `v2.3.4`, ≤ `v2.2.8`

**Patched versions:**

- wasmd `v0.70.4`, `v0.61.15`, `v0.60.9`, `v0.54.10`
- wasmvm `v3.0.8`, `v2.3.5`, `v2.2.9`

## Description of the bug

A code generation defect in the Wasmer Singlepass compiler, which wasmvm embeds to execute
CosmWasm contracts, allows a specially crafted contract to escape the WebAssembly execution
boundary and run controlled native instructions inside the node process. On an affected chain
this permits unauthorized minting of native tokens and permanent loss of user funds.

Exploitation requires an attacker to store and instantiate a contract they control. Where
`code_upload_access` and `instantiate_default_permission` permit it, that is reachable by any
ordinary funded account, with no governance action, privileged address, validator key or
collusion. A contract already stored on chain by an attacker remains a path even where those
parameters are restricted.

The resulting balances are indistinguishable from ordinary ones and survive a node restart, so
recovery requires coordinated remediation rather than restarting nodes.

We have received no reports of this vulnerability being exploited in production.

More detail will be added here once chains have had a chance to upgrade.

## Mitigations

There is no configuration only mitigation that removes the vulnerability.

Restricting `code_upload_access` and `instantiate_default_permission` to governance or an
allowlist raises the bar for delivery. Disabling `MsgStoreCode`, `MsgInstantiateContract` and
`MsgInstantiateContract2` blocks new delivery entirely. Neither neutralizes a contract that is
already stored on chain, and neither is a substitute for the patch.

## Patch

The patch upgrades the Wasmer dependency to a version that no longer contains the defective
code generation path. Cosmos Labs holds a license for Wasmer 7 Singlepass that covers all
downstream usage, so no separate agreement is required.

The patch is consensus breaking and requires a coordinated chain upgrade.

## Applying the patch

Chains MUST upgrade to the pair matching their release line:

- wasmd `v0.70.4` with wasmvm `v3.0.8`
- wasmd `v0.61.15` with wasmvm `v3.0.8`
- wasmd `v0.60.9` with wasmvm `v2.3.5`
- wasmd `v0.54.10` with wasmvm `v2.2.9`

If you use wasmvm without wasmd, upgrade to `v3.0.8`, `v2.3.5` or `v2.2.9` to match your line.

1. Check the current version: `go list -m github.com/CosmWasm/wasmd`
2. Bump the `github.com/CosmWasm/wasmd` dependency in your `go.mod` to the patched version for
   your line; `go mod tidy`; commit.
3. If you use the static libraries `libwasmvm_muslc.aarch64.a` / `libwasmvm_muslc.x86_64.a`,
   make sure you use the same version as your wasmvm version.
4. Check the updated version: `go list -m github.com/CosmWasm/wasmd`.
5. Follow your regular practices to deploy chain upgrades.

To confirm the correct library is loaded at runtime, run `<appd> query wasm libwasmvm-version`.
It must show `3.0.8`, `2.3.5` or `2.2.9` and must match the wasmvm version in your `go.sum`.

Maintained CosmWasm versions, and the policies that govern them, are documented at
<https://cosmwasm.github.io/maintainers/versions>. Versions outside the maintained lines are
affected and will not be patched. If you are running one, upgrade to the closest maintained
line above.
